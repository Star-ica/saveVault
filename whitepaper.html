SafeVault

Decentralized Multisignature Treasury Protocol

Network: BOT Chain (Chain ID 677)
Stack: Solidity ^0.8.20 · ethers.js v6 · Vanilla JS
Published: November 2026
Abstract. SafeVault is a non-custodial, on-chain multisignature treasury management protocol built on BOT Chain. It enables DAOs, startups, and project teams to collectively control treasury funds using configurable M-of-N approval thresholds. All proposals, approvals, and executions are recorded on-chain with no privileged backdoors. This document describes the protocol architecture, multisig logic, threat model, governance flows, and security assumptions.

1. Executive Summary

SafeVault provides shared custody of on-chain assets without requiring any trusted third party. A group of signers — identified by their wallet addresses — collectively governs a vault by proposing, approving, and executing transactions. No single signer can move funds unilaterally.

Key properties:

  • Non-custodial. Funds are held by the vault contract itself, not by any individual or service.
  • Configurable thresholds. Teams set their own M-of-N requirement at vault creation; this can be changed only through the proposal system.
  • No admin backdoor. The deployer of VaultFactory has no special power over individual vaults. Signers govern exclusively through proposals.
  • Transparent audit trail. Every proposal, approval, rejection, and execution is permanently recorded on BOT Chain and emits a queryable event.
  • BOT and ERC-20 support. Vaults hold and transfer both native BOT and arbitrary ERC-20 tokens using SafeERC20.

2. Protocol Architecture

2.1 System Overview

SafeVault consists of four smart contracts and a fully client-side HTML/JS frontend. No server infrastructure is required after deployment.

ContractRole
VaultFactoryDeploys new MultiSigVault instances, tracks all vaults globally
MultiSigVaultCore vault: holds funds, manages proposals, enforces thresholds
SignerRegistryDenormalized signer lookup for frontend queries
ProposalManagerRead-only query helper: paginated proposals, pending approvals per signer

2.2 Contract Hierarchy

VaultFactory └─ creates ──► MultiSigVault (one per team) ├─ holds BOT (native) + ERC-20 tokens ├─ Proposal[] proposals ├─ address[] signers └─ uint256 threshold SignerRegistry ◄── updated by VaultFactory on vault creation / signer changes ProposalManager ◄── reads MultiSigVault state for paginated queries

2.3 Data Flow

When a user interacts with the frontend:

  1. The browser connects to BOT Chain via MetaMask (ethers.js v6).
  2. VaultFactory is queried for vaults associated with the connected address.
  3. The selected MultiSigVault is queried directly for balances, signers, and proposals.
  4. Write operations (propose, approve, execute) send signed transactions to the MultiSigVault.
  5. Events emitted by the contract update the UI without any backend indexer.

3. Multisig Logic & Approval Thresholds

3.1 Threshold Mathematics

A vault requires at least M approvals out of N registered signers to execute any proposal. The threshold M must satisfy:

1 ≤ M ≤ N

Common configurations:

ConfigSigners (N)Required (M)Use Case
2-of-332Small team, one backup signer
3-of-553DAO committee, tolerates 2 absences
4-of-774Large DAO, strong decentralization
2-of-222Joint account, both must agree

3.2 Edge Cases

  • Signer removal below threshold: Removing a signer is only possible through a governance proposal that also adjusts the threshold if necessary. The contract rejects any signer removal that would make the threshold unreachable.
  • All signers approve: If all N signers approve, the proposal executes at the M-th approval — no need to wait for the remaining approvals.
  • Duplicate approval: The contract records per-signer approval status and reverts if the same signer attempts to approve twice.
  • Threshold change: Modifying the threshold is itself a proposal that requires the current threshold to be met before taking effect.

4.3 Execution Flow

The execute function follows the checks-effects-interactions pattern strictly:

function execute(uint256 proposalId) external nonReentrant onlySigner {
  Proposal storage p = proposals[proposalId];
  // CHECKS
  require(p.approvals >= threshold, "Below threshold");
  require(!p.executed, "Already executed");
  require(!p.cancelled, "Cancelled");
  // EFFECTS
  p.executed = true;
  emit ProposalExecuted(proposalId, msg.sender);
  // INTERACTIONS
  if (p.token == address(0)) {
    (bool ok,) = p.to.call{value: p.value}(p.data);
    require(ok, "BOT transfer failed");
  } else {
    IERC20(p.token).safeTransfer(p.to, p.tokenAmount);
  }
}

5. Governance & Signer Management

All governance actions — adding signers, removing signers, changing the threshold — are implemented as proposal types. This means they go through the same M-of-N approval process as financial transactions. There is no privileged admin function that can alter vault membership without signer consensus.

Governance Invariants

  • Threshold must always satisfy 1 ≤ threshold ≤ signers.length after any signer change.
  • Removing a signer whose removal would make threshold unreachable is rejected at proposal execution time.
  • A signer can propose their own removal (voluntary exit), subject to threshold approval.
  • The deployer of VaultFactory receives no ongoing governance power over any vault.
⚠️ Operational Warning If all signers of a vault lose access to their wallets simultaneously, the vault's funds become permanently inaccessible. Teams should maintain secure key backups and consider a recovery signer policy.

6. Token Support

SafeVault supports:

  • Native BOT — deposited via receive() or depositBOT(), transferred via low-level call in proposals.
  • Standard ERC-20 tokens — deposited via depositToken(address, amount), transferred via SafeERC20.safeTransfer to handle non-standard return values.
🚫 Fee-on-Transfer Tokens Tokens that charge a fee on transfer may credit less to the recipient than the proposal amount specifies. SafeVault does not adjust for this automatically. Teams should verify token behavior before including such assets in proposals.

Token Balance Display

The frontend reads balances using getBalance() (BOT) and getTokenBalance(address) (ERC-20). A known-tokens list is maintained in the frontend config; users can add arbitrary token addresses manually.

7. Threat Model

ThreatMitigationResidual Risk
Reentrancy attack on execute() ReentrancyGuard + checks-effects-interactions; state marked executed before external call Low — standard pattern applied consistently
Single signer compromised M-of-N threshold; compromised signer alone cannot execute Medium — if M=1, all risk falls on that key
Signer collusion (M signers collude) Protocol cannot prevent — this is a governance/social risk High for small M; teams choose their own tolerance
Front-running execute() Execution is idempotent once triggered; proposal marked executed before funds move Low — race condition does not benefit attacker
Phishing / malicious proposal UI shows full decoded calldata; signers must review before approving Medium — dependent on signer diligence
Griefing via spam proposals Optionally require a small BOT deposit per proposal (configurable) Low with deposit; Medium without
ERC-20 token approval exploit SafeERC20 used for all token transfers; no unchecked return values Low
Contract interaction proposals (arbitrary calldata) Signers see decoded calldata in UI; execution requires threshold approval Medium — depends on signer review quality

8. Security Architecture

8.1 Access Control

FunctionPermitted Callers
propose()Registered signers only
approve() / reject()Registered signers only; once per signer per proposal
execute()Any signer after threshold met; nonReentrant
cancel()Proposer or vault itself (via governance proposal)
depositBOT()Anyone (receive() is public)
depositToken()Anyone (caller approves ERC-20 first)
pause() / unpause()VaultFactory owner only (emergency use)

8.2 Invariants

  • A proposal cannot be both executed and cancelled.
  • A signer's approval is recorded as a boolean — the contract cannot double-count.
  • The threshold can never exceed the number of registered signers.
  • BOT is transferred using low-level call with return value checked; never transfer or send.

8.3 Pause Mechanism

The VaultFactory owner can invoke a global pause that halts new vault creation. Individual vaults may implement their own pause via a governance proposal. The pause mechanism is intended for emergency response only and does not grant the owner access to vault funds.

8.4 Audit Recommendations

ℹ️ Pre-mainnet Audit Before deploying SafeVault to manage significant treasury funds, a third-party Solidity audit is strongly recommended, with particular focus on: reentrancy in execute(), the signer management governance loop, and ERC-20 handling edge cases.

9. Deployment Guide Summary

See deploy.md for the complete step-by-step guide. In summary:

  1. Install Hardhat, OpenZeppelin, and dotenv.
  2. Configure hardhat.config.js for BOT Chain (chainId 677, RPC https://rpc.botchain.tg).
  3. Deploy in order: SignerRegistry → ProposalManager → VaultFactory.
  4. Verify all contracts on the BOT Chain explorer.
  5. Update the CONFIG block in index.html with deployed addresses.
  6. Serve index.html from any static host (GitHub Pages, IPFS, Cloudflare Pages).

Estimated deployment cost: ~1–3 BOT for all three contracts at standard gas prices.
